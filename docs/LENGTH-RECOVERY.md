# Адресное восстановление сохранённого CONSOLIDATE length — 2026-10-03

## Установленные факты

Начальный HEAD 412ac5d (feat/v1), дерево чистое, существующие материалы не изменены.
Два новых блока владельца получены из 0.1.26 на API34; содержание документов не получалось.
URL: attempt 4b28a508-9c6e-4b95-9169-87907d1ccad3, timestamp 1791056436671.
TEXT: attempt 0a790b3c-10f3-4bb5-ab51-2ba2787e3712, timestamp 1791056471353.
В обоих: REQUEST, CacheMissing, UNFINISHED_LENGTH, batchIndex=0, клиент 0/0.
Это ожидаемая **новая бесплатная остановка** до обращения к API, не новый ответ length и не BRIEF.

В 0.1.24 (09c540c) буквального состояния UNFINISHED_LENGTH не было. 0.1.26 вычисляет его из
Job.status != DONE && Job.finishReason == "length". В 0.1.24 callRaw сохранял finishReason из
LlmResponse, увеличивал attempts, добавлял usage; OpenRouterClient брал choices[0].finish_reason
или, при его отсутствии, native_finish_reason. Поэтому подтверждён сохранённый ответ с причиной
завершения length, но без исходного JSON нельзя различить эти два поля провайдера.

parseOrRetry в 0.1.24 сразу бросал TruncatedResponse при length (и на первом, и на втором ответе).
CONSОLIDATE ловил только InvalidResponse, общий обработчик превращал TruncatedResponse в UNKNOWN.
Новая информация подтверждает наличие именно этого дефектного пути в сохранённой работе и объясняет
наблюдаемую форму старого отказа. Она не восстанавливает стек каждого исторического события или
соответствие каждому старому timestamp. Нехватка денег не доказана как причина length/UNKNOWN.

savedBatchAttempts=1/3 — значение Job.attempts первого CONSOLIDATE пакета: количество успешно
возвращённых из llm.complete и учтённых ответов. Это не число запусков документа, не число всех
HTTP попыток и не число length. JSON-retry тоже добавляет ответ; HTTP 402 и внутренние неуспешные
транспортные попытки сюда не входят. При 3 последний ответ length, причины первых двух неизвестны.
Модель/провайдер, отправленный max_tokens/reasoning, токены и причина исчерпания лимита неизвестны.
Length не доказывает превышение входного контекста: мог закончиться бюджет выхода/reasoning.

## Подтверждённый дефект продолжения и исправление

0.1.26 продолжал PENDING CONSOLIDATE исходным пакетом до 40 лексических групп, без ограничения
размера входа и без деления; length превращался в fallback. Сохранённый length не менял следующий
запрос. Воспроизводящий тест (1 и 3 старых ответа) сначала провалился: ожидались два меньших запроса,
а отправлялся один исходный. Новый алгоритм:

- Старые успешные пакеты/явные fallback используются, их кэш не очищается.
- Старый незавершённый length сразу делит пакет пополам **между леммами/POS**. Исходный пакет
  заново не отправляется. Все вхождения одной лексической группы остаются вместе.
- Свежий length, включая JSON-retry, также делит пакет. Деление детерминированное, до одной группы.
- Дерево делений, активная часть и готовые ответы сохраняются в responseJson того же Job, без новой
  схемы Room. Части привязаны к полному входу SHA-256. После завершения дерево сводится к обычному
  родительскому ответу с восстановленными общими ID вхождений, который понимает прежний читатель.
- При повторном запуске готовые части пропускаются. После незавершённого ответа length активный путь
  позволяет разделить именно ту часть. Неуспешный HTTP не уничтожает готовые части.
- Если не помещается одна группа, фиксируется блокировка CONSOLIDATION_LIMIT. Вхождения не режутся,
  слова/примеры не отбрасываются; повтор того же дерева не вызывает модель опять. Нужна отдельная
  оценка модели/параметров или иной алгоритм, не автоматическая эскалация. Старый length-fallback
  для неделимой группы заменён этой безопасной остановкой; invalid-JSON fallback остался прежним.

Одна лемма не оказывается в независимых подзапросах, поэтому деление не создаёт карточки на каждое
упоминание и не разделяет одно значение по границам частей. Результаты применяются прежним механизмом
meaningKey; прогресс восстанавливается по lemma+meaning. Сохранение карточек/READY остаётся атомарным.

Проверка перед запросом: сериализованный ChatRequestBody (system, user, schema, параметры) в UTF-8
байтах + max_tokens + 1024 резерва сравнивается с сохранённым contextLength. Это консервативная
оценка, НЕ точная токенизация или гарантия всех шаблонов провайдера. Неизвестный контекст имеет
локальный защитный бюджет 32768, который не объявляется свойством модели. Явный лимит ответа не
увеличивается; недопустимый относительно известного maxCompletionTokens/contextLength останавливает
обработку. При отсутствующем max_tokens задаётся min(4000, известный положительный предел выхода).
Если вход велик, делится пакет; если велика одна группа — понятная остановка без потери данных.

Границы повторов: бинарное дерево из G≤40 групп содержит ≤2G−1 узлов, глубина ≤6. Один узел — один
ответ плюс максимум один JSON-retry; length не повторяет тот же узел, а делит его. OpenRouterClient
по-прежнему максимум 4 попытки на complete для transient ошибок, 402/обычный BAD_REQUEST не
повторяются автоматически. Грубый верх числа HTTP попыток на новое полное дерево — 8(2G−1), не
денежный предел. Реальных вызовов часто гораздо меньше: предделение без сети, готовые части, length
на первом ответе. Новый ручной запуск после сетевого/Payment сбоя может повторить незавершённую
часть. Между ответом сервера и его фиксацией в БД остаётся неизбежное окно повторной оплаты после
краша; ровно-однократную внешнюю оплату без поддержки провайдера не обещаем.

## Счётчики и инварианты

- sentences — сохранённые исходные предложения после сегментации: 745 / 599.
- segments — блоки перевода, каждый может охватывать несколько предложений: 725 / 580.
  Их различие допустимо. Проверяется полное и неперекрывающееся покрытие имеющихся предложений.
- rawUnits в 0.1.26 — длина u **последнего** прочитанного EXTRACT Job: 283 для index 11 из 12;
  2 для index 8 из 9. Это не сумма по документу и не число слов исходного текста.
- validatedUnits — сумма принятых единиц из всех Jobs: 3808 / 2765. Валидация может отбрасывать
  единицы; одна входная запись даёт не более одной принятой. Нет инварианта validated≤raw последнего
  Job, но есть validated≤суммы raw. Теперь имена rawUnitsLastJob и rawUnitsTotal однозначны.
- lexicalGroups — число групп лемма/POS после merge: 1371 / 1162, не итоговое число учебных карточек.
  Оно не превышает validatedUnits; одна группа может дать несколько значений/карточек.
- batches=6/4 — корневые пакеты только многопереводных групп, до 40 в пакете, не все lexicalGroups.
  Следовательно, многопереводных групп было 201–240 / 121–160. Точные количества/размеры из блока
  не восстановить. Все EXTRACT Jobs DONE, но это не доказательство смысловой полноты работы модели.
- Теперь дополнительно отвергаются перекрывающиеся диапазоны EXTRACT/Segment перед заменой карточек.
  Повторные поверхностные формы сами по себе допустимы; структурная проверка не доказывает, что модель
  нашла все значения или что исторический текст семантически корректен.

## UI и адресная команда

Бесплатный режим больше не выдаёт ожидаемую остановку за UNKNOWN: отдельные коды MISSING,
UNFINISHED, INVALID; LIMIT для неделимой группы/несовместимого лимита. Техническое событие сохраняется.
Старый блок 0.1.26 с CacheMissing получает понятное объяснение в UI по сохранённому подэтапу;
сам JSON старого события, его версия/код не переписываются задним числом.

«Продолжить консолидацию через API» → диалог → «Продолжить с расходами» — новая адресная команда.
Она использует сохранённые предложения, переводы и EXTRACT, обрабатывает только недостающие
CONSOLIDATE части. Не вызывает BRIEF, TRANSLATE, EXTRACT, извлечение источника, язык или STT,
даже если BRIEF раньше имел FAILED/fallback. Режим сохраняется в WorkManager Data, переживает
перезапуск; работа сериализуется тем же documentLock, перед новой работой старая отменяется/ожидается.

Используются сохранённые модели, temperature/reasoning и лимиты; новые текущие настройки не
подменяют snapshot. Для legacy с отсутствующей метаинформацией возможен бесплатный запрос каталога,
который заполняет только отсутствовавшие capabilities/лимиты. Исторически отсутствующие параметры
не объявляются известными. Неизвестная/несовместимая конфигурация может остановить запрос до API.
Обычный общий retry мог заново вызвать FAILED BRIEF; на экране CONSOLIDATING он заменён адресным
действием с подтверждением. Reprocess/«обработать заново» для этого восстановления не нужен.

## Стоимость и граница разрешения

Ни одного реального платного вызова в этом проходе. Для оценки нужны фактическая модель CONSOLIDATE
из snapshot, max_tokens, reasoning, поддержанные параметры, доступные маршруты/цены и лимиты модели,
размеры сериализованных частей и оценка выходных токенов (включая reasoning). Общих количеств
предложений/слов/групп недостаточно. Ключи, тексты, URL или полный payload не нужны для передачи.
Денежный предел технически не установлен и не обещан; диалог это прямо сообщает.

Владельцу: установить debug поверх 0.1.26 без очистки. Можно открыть документ/бесплатно повторить
консолидацию и скопировать новый понятный код. Для платного продолжения подготовлено указанное
действие, но **остановиться до «Продолжить с расходами»**, пока владелец отдельно не решит запускать
платную работу. Автоматического перехода от бесплатной команды к платной нет.
