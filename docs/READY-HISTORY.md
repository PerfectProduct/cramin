## Что доказано кодом 0.1.28

1. requeue меняет статус на QUEUED, сохраняет прежний failureJson. Во время работы статусы меняются
   по стадиям. onFailureDiagnostic вызывается на неуспехе отдельной клиентской попытки, в том числе
   перед разрешённым внутренним повтором. Он пишет failureJson, но сам не ставит Document.FAILED.
2. При IOException OpenRouterClient использует захваченные параметры начала запроса без response
   metadata. IOException возможен до получения ответа И при чтении тела уже пришедшего ответа.
   Поэтому отсутствие respondedAt/httpStatus не доказывает, что сервер не ответил/не обработал запрос.
   Другие клиентские ошибки тоже не равны терминальному отказу всего документа.
3. После transient ошибки следующий HTTP retry может успешно завершиться. Карточки записываются
   целиком вместе с READY и завершением reprocess snapshot в одной транзакции. errorCode/errorMessage
   очищались, **failureJson оставался**. StatusBanner показывал «Последний отказ» без проверки статуса.
   Это подтверждённый дефект отображения и воспроизводимый путь к показанному виду экрана.
4. Если обработка в итоге бросает исключение, общий обработчик сохраняет терминальную диагностику
   и FAILED. Если commit READY уже произошёл, последующая ошибка уведомления/очистки не отменяет его.
   При отмене исключение пробрасывается; промежуточный блок может остаться и при незавершённой работе.

Телефонная запись совместима с transient IOException → успешный повтор → READY. Но по скриншоту
и старому блоку **не доказаны текущий Document.status, полнота пакетов и точная сетевая причина**.
Наличие карточек/кнопки обучения само по себе этого не доказывает: старые карточки могут сохраняться
при текущем FAILED/обработке. UNKNOWN — неизвестная классификация события, а не свидетельство того,
что весь документ сейчас неисправен. Старую запись не дополняем догадками о результате HTTP.

## Завершение и полнота

До writeCards проверяются покрытие предложений переводами, DONE EXTRACT с JSON/диапазонами,
валидация единиц. Для всех вычисленных корневых пакетов (только многопереводные лексические группы)
используется готовый ответ либо обходятся все необходимые части дерева. Незавершённая/заблокированная
часть бросает исключение; writeCards не вызывается. Ветки делятся между леммами/POS, не между
упоминаниями одной леммы. Затем атомарно заменяются все карточки, senses/occurrences, прогресс и READY.
Транзакция не делает частичный успешный commit; тесты отказа внутри замены проверяют rollback.
Преждевременный READY из-за самого разбиения не обнаружен.

Consolidation.apply проверяет покрытие ID группы ровно один раз. Невалидная/неполная группа ответа
не даёт частичного набора: действует существующий консервативный fallback по различным переводам,
который сохраняет все единицы. Это логическая полнота покрытия, а не доказательство качества модели
или идеальной эквивалентности синонимов. После свёртки старых частей история использования fallback
может быть недоступна; новая сводка это явно отмечает, не выдавая её за проверенный успешный ответ LLM.

MeaningKey объединяет одинаковые нормализованные переводы внутри lemma/POS; UNIQUE индекс
(documentId,lemmaKey,meaningKey) не даёт продублировать такую карточку. 1162 лексические группы могут
дать 1240 значений, поэтому сами эти числа допустимы и не устанавливают ошибку.

## Исправление состояния и UI

- READY показывает «Восстановлено · документ готов», историю раскрывают отдельно. Текущий статус
  берётся из Document, **не из числа карточек**. FAILED сохраняет текущую ошибку; работающие стадии
  показывают «Обработка продолжается · диагностика предыдущих событий».
- Исторический блок называется событием, не обязательно окончательным отказом. Последний сохранённый
  диагностический блок не удаляется. Полный журнал всех прошлых запросов приложение не хранит.
- Новые успешные завершения атомарно добавляют recoveredAt и recoveryAttemptId к сохранённому событию
  вместе с READY. Это завершение документа, а не фиктивный successful response исходного HTTP запроса.
- Для уже сохранённого READY старый JSON не переписывается; UI использует реальный статус немедленно
  после обновления. Время восстановления остаётся UNKNOWN, если его раньше не записали.
- Новый origin различает CLIENT_ATTEMPT_ISSUE, TERMINAL_PROCESS_FAILURE и LEGACY_UNKNOWN. Старые
  события остаются LEGACY_UNKNOWN; им не присваивается задним числом конкретная причина.

## Корреляция

Прежний request.attemptId генерировался на **каждую HTTP попытку**, а не на весь документ. В новом
блоке это поясняется. Добавлены processingAttemptId (один запуск DocumentProcessor), logicalRequestId
(один complete, включая внутренние HTTP retries), jobIndex и путь части L/R. Внутренний HTTP retry
имеет новый attemptId, но те же processing/logical IDs. Новая часть — новый logical ID; новый запуск —
новый processing ID. Local event использует тот же processing ID. RecoveryAttemptId хранится отдельно
от ID исходного события. Транспортная ошибка отмечается RESPONSE_NOT_RECORDED, не «ответа не было».
Никакие параметры старого события не заменяются текущими настройками или успешным новым запросом.

## Бесплатная сводка состояния

«Скопировать диагностику» всегда доступно и читает согласованный snapshot Room без API/Worker,
изменений данных и повторной генерации. Отдельные разделы:

- текущее состояние, прогресс, время копирования, updatedAt (явно НЕ время завершения), Source;
- количества Sentence/Segment/Card/Occurrence и Job по kind/status;
- повторная локальная проверка покрытия переводами, DONE EXTRACT и диапазонов, требуемых пакетов
  CONSOLIDATE, читаемости/привязки сохранённых ответов; восстановление ожидаемых ключей значений
  и числа вхождений и сравнение с реально сохранёнными карточками;
- MATCHES_SAVED_PIPELINE_RESULTS, UNFINISHED_JOBS, MISSING_CACHE, CARDS_OR_OCCURRENCES_DIFFER либо
  UNREADABLE_OR_INCOMPATIBLE_CACHE. Это структурная сверка, не оценка содержимого/семантики;
- историческое событие с отдельным disposition по текущему статусу документа.

Не копируются заголовки, текст, леммы/переводы, URL, пути, payload, БД, ключи или произвольные сообщения
исключений. Внутри проверки тексты читаются локально для прежней валидации, наружу выходят только
счётчики/статусы. При работающем документе отчёт описывает момент чтения, а не обещает конечный исход.
BRIEF FAILED/fallback допустим и не означает незавершённость обязательных этапов консолидации.
